## Files and operation

[evidence: delivered files] My implementation files are `capability/standard/{__init__,definition,check,render}.py`, generated `capability/standard/STANDARD.md` and `capability/standard/PATTERN.template.md`, `capability/check_contribution.py`, and `capability/tests/test_standard.py`. No `USE.md`, store/access code, project configuration or other-project files were written. Generated bytecode from validation was removed.

From any working directory, use Python with an explicit path to the clone's `check_contribution.py` and the contribution directory; append `--json` for the result envelope. Exit 0 means complete mechanical presence, 1 incomplete/invalid/unknown required material, 2 usage or read failure. Human review remains required after exit 0. The check reads the specified bundle and does not execute its kit or fetch evidence. Its implementation and tests invoke no shell.

To regenerate documentation, from the capability root run `python -m standard.render`. `python -m standard.render --check` exits unsuccessfully if either generated artifact is stale. The field table, required section descriptions, conditional requirements, predicate and review items are rendered from the same definition consumed by the checker; the generic interpreter contains no separate field inventory.

## Record interface held for the sibling

[evidence: `capability/standard/definition.py`, RECORD and CONDITIONS] Record format is `schema_version: 1`, governing `standard_version: "1.0"`. Full field names and conditional rules are in generated `standard/STANDARD.md`. The approved record shape is retained with the five adjustments; all defined keys are required. Nulls preserve unknown knowledge and prevent full presence except for explicitly inapplicable verification details. Empty suitability/limit lists mean none identified and trigger the standing review obligation, not a universal-fit assertion.

The JSON top-level keys are `schema_version`, `standard_version`, `id`, `origin`, `applicability`, `evidence`, `limits`, `evolution`, `assets`. Each asset's `context_ref` resolves either to a PATTERN.md section slug or to a JSON field through `PATTERN.md#/...`. Kit paths are portable relative paths under `kit/`; every ordinary kit file must appear once in the asset inventory. Dates use ISO calendar dates; reported checked evidence requires checker identity, date, scope and result. Unchecked/unavailable evidence requires a reason and can leave those check details null. At least one dated, locatable successful-use account is required for mechanical completeness, while failures and mixed outcomes remain preserved.

[evidence: `capability/standard/check.py`] Public imports are `from standard import check_contribution, discovery_record`. `check_contribution(path)` returns `standard_version`, `record`, `discovery`, `checks`, `presence_complete`, `review_required`, `limitations`, `read_error`. Every diagnostic contains `rule_id`, `field`, `state`, `message`. Missing or malformed material stays visible; malformed JSON returns null record/discovery. Duplicate JSON keys and nonstandard JSON constants are rejected.

`discovery_record(record, pattern_text)` derives the compact projection from full context and its single authored prose. The optional second parameter defaults to empty prose for callers that only have a record; such callers get blank text, not invented metadata. The checker passes the actual source and adds `presence_complete` and `has_unknowns` to the projection. Discovery carries identifiers/versions, title, summary, problem, bounded positive/negative fit, limits and unknowns indicators, reported evidence outcomes and verification states, asset kinds, `screening_only`, and `context_ref: PATTERN.md#context-record`.

[evidence: measurement with `tests/test_standard.py`'s invented bundle] Compact JSON serialization with separators `(',', ':')` and UTF-8 was **453 bytes per synthetic contribution**, versus **1,118 bytes** for its full JSON record, excluding the prose and assets. This is a representative fixture measurement, not a corpus average or token claim. Title/summary/problem caps are 96/180/120 characters; positive and negative fit each retain at most two conditions of 96 characters. Identifiers/version strings are capped at 64 characters and asset kinds at four values of 32 characters. Evidence statuses/outcomes are bounded vocabularies. Unicode escaping can increase serialized byte size. Truncation deliberately loses detail: the sibling must retain full context and the bundle for selection, and supply its own resolvable bundle locator alongside the contribution-relative context reference.
